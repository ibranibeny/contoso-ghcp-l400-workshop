// Overview

Why this workshop

GitHub Copilot has moved from suggesting the next line to running agents that plan, change code across files, run tests and open pull requests for review. This session is for Contoso engineers who already code with Copilot and want to go deeper: understand the mechanics, set the guardrails, and package team know-how as reusable agents and skills.

Who should attend

  • Software engineers and tech leads (web, API, data, mobile)
  • Architects, platform and DevOps engineers
  • QA and test-automation engineers
  • Comfortable with Git, pull requests and an IDE; prior Copilot use expected

What you will leave with

  • A working model of how Copilot builds context, picks models and runs the agent loop
  • A clear rule for GitHub Copilot vs Microsoft 365 Copilot, and how they work together
  • Your own Agent Skill and custom agents, committed to a repository
  • A take-home lab: delegate a pull request to Copilot cloud agent and review it like a senior engineer
  • A scored shortlist of full-stack app ideas for Contoso, with a first spec drafted with superpowers
  • The demo's contoso-fullstack-docker skill, ready to reuse for your own apps

Ground rules for the day

  • Synthetic data only: no production data, customer data or secrets in prompts or repositories
  • You own every line an agent writes: review, test, then merge
  • Least privilege for agents and tools; approve actions deliberately
  • Everything runs locally in Docker on your laptop; no cloud subscription needed
  • Ask anything, anytime: at L400 we follow your questions

01

Overview: GitHub Copilot and the agentic SDLC

15 minTalk + demo

What we cover

  • The arc: inline completions and next edit suggestions, then chat, then agent mode in the IDE, then asynchronous agents on GitHub (Copilot cloud agent, formerly coding agent), and now parallel agent sessions in the GitHub Copilot app and Copilot CLI.
  • One Copilot, many surfaces: VS Code, Visual Studio, JetBrains IDEs, Eclipse and Xcode; GitHub.com (chat, cloud agent, code review, Spaces); the terminal; the desktop app; GitHub Mobile.
  • Three ways to work with agents: collaborative (you steer and approve), asynchronous (you delegate, then review) and automated (an event or schedule starts the agent).
  • What changes for engineers: less typing; more specifying intent, curating context and reviewing outcomes. Accountability stays human.

Demo (5 min) · one backlog item, three ways: agent mode live in VS Code; Copilot CLI and a Copilot cloud agent session started from a GitHub issue, both prepared before the session.

02

Definition: how GitHub Copilot works under the hood

20 minDeep dive

Working definition. GitHub Copilot is an AI coding assistant that spans the software lifecycle (in the IDE, on GitHub.com, in the terminal and in a desktop app) with agents that can plan, act through tools and hand back reviewable changes.

Request lifecycle

  1. ClientIDE, CLI, app or GitHub.com gathers context
  2. Copilot serviceidentity, policies, content filters
  3. Modelpicked by you or Auto; bring your own key where enabled
  4. Post-processingfor example public-code matching and references
  5. Client actsapplies edits, runs tools, iterates

L400 deep dive

  • Context engineering by mode: Ask uses your selection, open files, the semantic index and chat history; Plan adds the goal, related files and project context; Agent adds a workspace summary, tool descriptions, MCP servers and terminal or test output. Instructions ride along in every mode.
  • Instruction layering: personal and organization instructions, repository-wide .github/copilot-instructions.md, path-specific *.instructions.md with applyTo, and AGENTS.md; curated context through Copilot Spaces and Copilot Memory.
  • Models and cost: multi-model choice, Auto model selection and bring-your-own-key; match model capability to task complexity and watch usage.
  • The agent loop: plan, call a tool, observe, adjust. Tool approvals, local and cloud sandboxes, and the cloud agent's ephemeral environment set the blast radius.
  • Enterprise guardrails: enterprise and organization policies, AI Controls for agents, content exclusion, audit logs, usage metrics (dashboard and API) and OpenTelemetry for agent monitoring.

Demo (5 min) · open the chat debug view and logs to see what Copilot actually sent, then fix a weak answer by improving context instead of re-prompting.

03

When to use GitHub Copilot: positioning vs Microsoft 365 Copilot

15 minTalk + discussion

Decision rule. Choose by where the work lives and where the assistant must act. If the output is software that must pass review, tests and a release process, start with GitHub Copilot. If the output is knowledge work grounded in email, meetings, chats and documents, start with Microsoft 365 Copilot.

Primary usersDevelopers, tech leads, platform and DevOps, QAEveryone: business, operations, management, IT

Better together at Contoso

Requirements to pull request

Microsoft 365 Copilot turns meeting notes and documents into a requirements brief; engineers turn it into GitHub issues; Copilot cloud agent drafts the change; Copilot code review and humans approve it.

Pro-code agents for Microsoft 365

Build a Microsoft 365 Copilot agent or Cowork plugin with Microsoft 365 Agents Toolkit or Work IQ Dev Tools, and use GitHub Copilot to implement the API or MCP server behind it. The Microsoft 365 tooling still owns packaging, publishing and runtime.

One skill format, two worlds

Agent Skills (SKILL.md) is an open standard used by GitHub Copilot and by Copilot Cowork plugins. Design a skill once, then validate it on each host, because supported features differ.

Start agents where people talk

Copilot integrations let teams start Copilot cloud agent from tools such as Microsoft Teams or Azure Boards, with the conversation as context.

Anti-patterns · shipping production code generated outside the SDLC (no repository, no tests, no review); using a coding agent for document-heavy business workflows; treating one Copilot as a substitute for the other.

Quick poll (3 min) · three tasks from your week: which Copilot would you use for each, and why?

04

What is an agent? What is a skill?

25 minDeep dive + live build
Agent

An AI system that completes a goal on your behalf. Unlike an assistant that only answers, it plans, uses tools to act, inspects the results and adjusts, while you define the goal and constraints, grant access and review the work.

Paraphrased from GitHub Docs, “About GitHub Copilot agents”.

Skill

A folder of instructions, scripts and resources, anchored by a SKILL.md file, that Copilot loads only when it is relevant, so specialised workflows don't bloat every conversation.

Paraphrased from GitHub Docs, “Agent skills”.

// Runs on your laptop · WSL 2 + Docker Engine

Docker guide: WSL 2, Docker Engine and the lab stack on your laptop

No cloud account and no Docker Desktop licence are needed. On Windows laptops the lab runs in Ubuntu on WSL 2 (Windows Subsystem for Linux) with Docker Engine, and the three containers (web front end, API and PostgreSQL) start with one Docker Compose command. Do steps 1 to 3 before the day: about 45 minutes, including one restart. Steps 4 to 8 happen during the labs.

Why WSL 2 + Docker Engine · Docker Desktop needs a paid subscription for professional use in organizations with 250 or more employees or USD 10 million or more in annual revenue. Docker Engine, with its Buildx and Compose plugins, is open source (Apache 2.0) and runs inside Ubuntu on WSL 2, so the workshop needs no Docker licences. From step 2 onwards every command is the same on Windows (in Ubuntu) and on Linux.

Check with Contoso IT first · installing WSL needs administrator rights once (or an IT-run install), hardware virtualization turned on and a device policy that allows WSL. From inside WSL, laptops must reach the Ubuntu archive, download.docker.com, Docker Hub, PyPI, npm, GitHub and the VS Code Marketplace. If traffic goes through a proxy or TLS inspection, get the proxy address and the root certificate before the day.

Step 1 · Windows: install WSL 2, Ubuntu and Docker Engine Before the day

1a
Windows · 2 min

Check the laptop

Windows 10 version 2004 (build 19041) or later, or Windows 11, 64-bit. 16 GB RAM recommended (8 GB minimum) and 20 GB of free disk.

  • Virtualization must be on: Task Manager › Performance › CPU shows Virtualization: Enabled. If it doesn't, turn it on in BIOS/UEFI or ask Contoso IT.
  • Docker Desktop already installed? Quit it and uninstall it, or at least turn off its WSL integration for Ubuntu. Docker warns that running Docker Desktop alongside an engine installed inside a WSL distribution can cause conflicts.
# PowerShell
cmd /c ver     # 10.0.19041 or higher
1b
Windows · 15 min + restart

Install WSL 2 and Ubuntu 24.04

Open PowerShell as administrator (right-click › Run as administrator), run the install, then restart Windows. New installations use WSL 2 by default.

  • After the restart, open Ubuntu 24.04 from the Start menu if it hasn't opened by itself, and create a Linux user name and password. That password is the one sudo asks for.
  • We use Ubuntu 24.04 LTS: Docker supports it, and its Python 3.12 matches the lab's API image.
  • Stuck at 0.0%? Add --web-download to the install command. Name not found? wsl --list --online shows the exact names.
# PowerShell as administrator
wsl --install -d Ubuntu-24.04

# after the restart, in PowerShell
wsl --version    # WSL version 2.x
wsl -l -v        # Ubuntu-24.04   Running   2
1c
Ubuntu · 2 min

Check that systemd is running

Docker Engine runs as a systemd service. Ubuntu installed with wsl --install uses systemd by default, so this is usually just a check.

  • If the check prints anything other than systemd, add the two lines to /etc/wsl.conf with sudo nano /etc/wsl.conf.
  • Then run wsl --shutdown in PowerShell, wait about 8 seconds and open Ubuntu again.
# Ubuntu
ps -p 1 -o comm=    # expect: systemd

/etc/wsl.conf (only if needed)

[boot]
systemd=true
1d
Ubuntu · 10 min

Install Docker Engine from Docker's apt repository

These commands follow Docker's official guide for Ubuntu. Run them in the Ubuntu terminal; sudo asks for your Linux password and apt install asks you to confirm.

  • The first command removes unofficial Docker packages; apt may report that none are installed.
  • Docker starts automatically whenever Ubuntu starts.
  • Later updates come through apt: sudo apt update && sudo apt upgrade.
# 1. Remove conflicting packages
sudo apt remove $(dpkg --get-selections docker.io docker-compose \
  docker-compose-v2 docker-doc docker-buildx podman-docker \
  containerd runc | cut -f1)

# 2. Add Docker's GPG key and apt repository
sudo apt update
sudo apt install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update

# 3. Install Docker Engine with Buildx and Compose
sudo apt install docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo docker run --rm hello-world    # Hello from Docker!
1e
Ubuntu + PowerShell · 2 min

Run Docker without sudo

Add your Linux user to the docker group, then restart WSL so the change applies everywhere, including VS Code.

  • Docker notes that the docker group grants root-level privileges inside Ubuntu. If Contoso policy doesn't allow that, skip this step and type sudo docker instead.
# Ubuntu
sudo usermod -aG docker $USER

# PowerShell: restart WSL, wait ~8 seconds, open Ubuntu again
wsl --shutdown

# Ubuntu
docker run --rm hello-world     # now without sudo

Not on Windows?

Linux (Ubuntu 22.04, 24.04 or 26.04 LTS)

Docker Engine runs natively · no WSL needed

  1. Run the commands from step 1d in your terminal.
  2. Run sudo usermod -aG docker $USER from step 1e, then log out and back in instead of wsl --shutdown.

macOS

Docker Engine doesn't run on macOS directly

  1. Docker Desktop for Mac needs a paid Docker subscription at Contoso's size. If Contoso provides one, install the Apple silicon or Intel build and continue at step 2.
  2. Otherwise, pair with a colleague whose laptop runs WSL 2 or Linux for the labs.

Build the images

Two images are built from source; the database uses the official PostgreSQL image. The web image is multi-stage (Node builds, Nginx serves), and the API copies its dependency list before the code so the dependency layer stays cached.

In the lab

Deploy the stack on your laptop

One command creates the network, the volume and three containers. Compose starts the API only after the database reports healthy, and the web front end only after the API does.

  • App: http://localhost:8080 · API docs: http://localhost:8000/docs. Open them in your Windows browser: WSL forwards localhost to Windows.
  • The database has no host port; reach it with docker compose exec db psql.
docker compose up -d --build
docker compose ps     # db, api: healthy

compose.yaml

services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: lab
      POSTGRES_DB: copilot_lab
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set it in .env}
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U lab -d copilot_lab"]
      interval: 5s
      retries: 10
  api:
    build: ./api
    environment:
      DB_HOST: db        # the service name, not localhost
      DB_NAME: copilot_lab
      DB_USER: lab
      DB_PASSWORD: ${POSTGRES_PASSWORD}
    ports: ["${API_PORT:-8000}:8000"]
    depends_on:
      db: { condition: service_healthy }
    healthcheck:
      test: ["CMD", "python", "-m", "app.healthcheck"]  # GET /health
      interval: 10s
      retries: 5
    develop:
      watch:
        - { action: sync+restart, path: ./api/app, target: /app/app }
        - { action: rebuild, path: ./api/requirements.txt }
  web:
    build: ./web
    ports: ["${WEB_PORT:-8080}:80"]
    depends_on:
      api: { condition: service_healthy }
  smoke:     # on demand: docker compose run --rm smoke
    image: python:3.12-slim
    profiles: ["test"]
    environment:
      SMOKE_CHECKS: http://api:8000/health,http://web/,http://web/api/health
    volumes: ["./tests/smoke:/smoke:ro"]
    command: ["python", "/smoke/smoke_test.py"]
volumes:
  pgdata:

Stop and clean up

Stopping keeps your data in the pgdata volume. Add -v to reset the database to the seed data on the next start.

docker compose down -v    # stop and reset the database

- Multi-stage builds; copy dependency files before source.
- Run as non-root; give every service a healthcheck.
- Secrets stay in .env (git-ignored), never in images.
- Call other services by name (db, api), not localhost.

THE SKILLS

superpowers + contoso-fullstack-docker

Process skills say how we work; the golden-path skill says what we build with and how we run it. Copilot loads each skill only when its description matches the task.

THE APP

JagaJalur: Pipeline Patrol and Work Order Hub

Patrol officers log findings along pipeline segments, HSSE supervisors triage them, critical findings become work orders with an SLA, and maintenance planners track them to closure.

  • Stack: React + TypeScript (Vite) on Nginx, FastAPI, PostgreSQL 17, Docker Compose; UI in Bahasa Indonesia
  • Data: pipeline segments, patrol findings, work orders and an audit log; synthetic seed of 12 segments, 40 findings and 10 work orders
  • Quality: 54 pytest tests, a five-URL smoke test, problem+json errors, an audit entry for every change

Why this app · it sits on Contoso's safety-critical pipeline operations, connects field, HSSE and maintenance teams, and is safe to demo because it needs no customer or commercial data.
